## Accounting interpretation

The existing ledger uses a single signed `amount` per transaction and explicitly adjusts `Account.balance` in the write transaction. For income, the balance increases; for an expense, it decreases; for transfer, the source decreases and destination increases via `transferAccountId`; void reverses the signed effect. Test oracles use the persisted transaction type/status semantics implemented by the repository. Investment/assets generally do not post to an account ledger.

## Remaining reconciliation gaps

- Refund/void policy and preserving original transaction facts need a product/accounting decision; no refund feature was implemented.
- Account overdrafts are accepted by the UI path; no configured overdraft policy was found.
- Reports render unrelated fixed sample totals and fail household reconciliation.
- Investment create does not post or connect account movement in the current API; asset/liability creates are balance-sheet metadata only.
- No browser check for transfer, browser second-household isolation, browser report data filtering, or bill payment completion (native number field automation retained old value during partial-payment attempt).
