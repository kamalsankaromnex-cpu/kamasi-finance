# AI FINANCIAL ASSISTANT POLICY

## Core Architectural Invariants

### 1. LLM Authority & Boundary Rule
The LLM has **zero authority** over financial truth. It may interpret user natural-language queries, request approved tools from the `FinancialQueryEngine`, and format natural-language explanations, but it MUST NOT:
- Independently calculate authoritative account balances or transaction totals.
- Query raw database tables or Prisma repositories directly.
- Modify financial records outside validated command schemas.
- Execute financial mutations without explicit user confirmation of an immutable, parameter-hashed `FinancialActionProposal`.

---

### 2. Single Data Gateway Rule (`FinancialQueryEngine`)
All financial data supplied to the AI assistant MUST pass through `FinancialQueryEngine` (`src/finance/ai/query-engine.ts`). Direct database queries, raw repository calls, or arbitrary SQL execution from the AI layer are strictly prohibited.

---

### 3. Tool Allowlisting
The AI assistant is strictly limited to the following registered tools:
- `get_spending_analysis`: Categorized expense analysis over date ranges.
- `get_income_summary`: 10 Universal income streams analysis.
- `get_goal_status`: Goal progress, required contributions, shortfalls.
- `get_liability_summary`: Outstanding balances, EMI pay-down, simulated settlement.
- `get_investment_performance`: Realized vs unrealized gain/loss, cost basis, valuation.
- `get_net_worth_analysis`: Net worth actuals and trajectory projections.
- `run_scenario_simulation`: Forecast query delegating directly to `FinancialForecastingService`.
- `propose_financial_action`: Action proposal generator.

Any tool request outside this registry MUST be rejected.

---

### 4. Structured Query Envelope (`FinancialQueryResult<T>`)
Every query engine function returns a standardized envelope:
```ts
export interface FinancialQueryResult<T> {
  queryId: string;
  generatedAt: string;
  period?: { from: string; to: string };
  currency: string;
  data: T;
  source: "ledger" | "reporting" | "forecast";
}
```

---

### 5. AI Response Contract (`AIResponse`)
All responses generated by the AI assistant MUST conform to the structured contract:
```ts
export interface AIResponse {
  answer: string;
  facts: Array<{ label: string; value: number | string; currency?: string }>;
  calculationsUsed: string[];
  assumptions: string[];
  warnings: string[];
  sourceQueryIds: string[];
}
```
Every numerical claim in `answer` MUST map directly to an entry in `facts` sourced from a verified `sourceQueryIds`.

---

### 6. Action Proposal & Parameter Hash Binding Workflow
Financial mutations requested via natural language follow the strict pipeline:
1. **AI Action Proposal Generation**: `propose_financial_action` generates a `FinancialActionProposal` with a unique ID, expiration timestamp (e.g., 15 minutes), and SHA-256 parameter hash (`parametersHash`).
2. **User Explicit Confirmation**: The user reviews the proposal and submits explicit confirmation via `POST /api/ai/execute-action`.
3. **Hash Verification & Execution**: The execution endpoint re-computes the parameter SHA-256 hash. If `parametersHash` matches and proposal status is `PENDING` (not `EXPIRED`), a `FinancialCommand` is dispatched to `LedgerService` using a deterministic `idempotencyKey`.

Direct LLM-to-database mutations are strictly forbidden.

---

### 7. Security & Prompt Injection Defense
Authorization and data isolation are enforced at the API and data-access layer:
- User prompts CANNOT override household boundaries or security policies.
- System prompts are supplemented by strict request-level household authorization check (`authorizeRequest`).
- Raw database credentials, API tokens, and user password hashes are excluded from AI contexts.
